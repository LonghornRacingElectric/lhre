# cand

CAN daemon — the input side of BEVO. Reads both FDCAN buses via SocketCAN,
decodes frames using compiled tables generated by Bazel from `lib/spec`, merges
NMEA GPS from a TCP/UDP listener, and publishes protobuf
(`OrionSensorData`) snapshots to the other daemons over Unix sockets.

- `:cand` — the real daemon. Real CAN reading is Linux-only (`socketcan`);
  on macOS it compiles to a stub that tells you to use `mock_main`.
  `CAND_USE_MOCK=1` switches the CAN readers to UDP ports 5005/5006 without
  hardware.
- `:mock_main` — full cand replacement that fabricates plausible data;
  works anywhere with Unix sockets.
- `:mock_can` — pure-Python UDP traffic generator feeding
  `CAND_USE_MOCK=1` cand.
- `:run_can_stack` / `:run_mock_can_stack` — launch the whole daemon fleet
  (see the scripts for the wiring).

The physical stack launcher requires `BEVO_CORE_RELEASE_ROOT` containing an
[updater-generated plan](../updater/README.md) for the same compiled schema
as its Bazel-built executables. `publishd` requires that plan before it can
release cand's startup semaphore. The mock launcher without `publishd` is
unaffected.

Config is via `CAND_*` env vars (interface names and publish rate).
The CAN mapping is compiled into the executable; there is no runtime JSON
file or `CAND_CAN_JSON_PATH` override. Change the textproto and rebuild the
executable instead. The CAN readers, IPC framing and publish loop are unchanged.
