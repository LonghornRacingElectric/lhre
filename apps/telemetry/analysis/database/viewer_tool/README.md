# viewer_tool

Next.js viewer for live telemetry and replay workflows.

## Artemis applications

Artemis history, discovery and live reads use the query gateway. Set
`QUERY_GATEWAY_URL` and `QUERY_API_TOKEN` on the viewer server; the token is never
sent to browser code. Sign in normally, then use `/trackside-live`.
`/live-viewer` redirects there. Artemis requires a configured gateway and does
not silently substitute sample telemetry.

Live widgets use native `sensor_data` through `/v1/stream`; the gateway owns the
Kafka consumer. The viewer converts snake_case fields at the widget boundary.
Trackside converts Artemis GPS speed from knots to m/s. Angular wheel speed is
not used as vehicle speed without a wheel radius. Voltage/current can supply
power when an explicit power channel is absent.

Status events include Kafka lag and latest sample/observation timestamps.
Connection readiness alone does not establish freshness. Widget samples are a
latest-value view of independently arriving fields; they are not an atomic
cross-pool measurement. Query streams replace bounded windows. Historical
pagination errors discard the partial request and require a new query.
Trackside uses sample time for its freshness badge, marks Kafka backlog as
delayed, and reconnects after coverage gaps.

## Signal discovery

`GET /api/cars/artemis/signals` uses the authenticated gateway's deployed
`/v1/signals`, with its hash in `X-Schema-Version`. A requested version must
match the deployed version. Trackside channel discovery uses the same catalog
and units. Scalar numeric channels support charts; GPS arrays have explicit
latitude/longitude projections in the historical adapter.

Historical Orion tools retain their file-based catalogs, generated with
`bazel run --config=local //tools/spec:publish_signals`. Those archives use
`SIGNAL_CATALOG_DIR` and support exact versions and rollback through
`current.json`; see the [archive guide](../../../catalogs/README.md).

The legacy Orion Kafka/bus routes remain for historical workflows. Artemis
logical widget topics are normalized from the gateway's native feed; optional
derived processor topics can still be requested explicitly.

Run `npx vitest run --config vitest.config.mjs` for application tests and
`npx tsc --noEmit` for type checking. The [demo guide](../README.md) covers
publishing and the provisioned Grafana dashboard.

## Historical queries

`POST /api/query` reads Artemis's generated Timescale frequency pools using its
published signal catalog. It returns raw JSON/CSV pages ordered by timestamp,
recording session, nanosecond receipt time and signal. Its cursor has no packet
identifier; `sample_time_ns` is a decimal string in JSON/CSV. Other car
names are rejected; Orion's existing telemetry readers remain separate legacy
integration paths. The gateway does not migrate or reconcile databases.

Set `QUERY_GATEWAY_URL` and `QUERY_API_TOKEN` on the viewer server. Configure
database connections and `QUERY_CURSOR_SECRET` on the gateway. See the
[query guide](src/lib/query/README.md) for limits and pagination behavior.
Existing bucketed Artemis analysis remains available through the MoTeC interfaces.

`npm run test:query` runs the gateway's Bazel functionality checks. Real
Kafka/Timescale/Grafana checks are described in the [test guide](tests/query/README.md).

## Local setup

The viewer, the Prisma seed scripts, and the docker compose stack all read one
`.env` at the repository root (`cp .env.example .env`).

Install deps. The `postinstall` hook generates the `auth`, `telemetry`, `orion`, and
`artemis` Prisma clients into `.prisma/` and runs `prisma db push` on the auth
SQLite file (`AUTH_DATABASE_URL`) so it matches `prisma/auth.prisma` — there are
no migrations, and the committed `prisma/dev.db` predates `User.isAdmin`:

```bash
npm install
```

To create a login during install, set `VIEWER_USERNAME` and `VIEWER_PASSWORD`
(and `VIEWER_ADMIN=1` for an admin) in the root `.env`; the user is upserted, so
reinstalling resets the password. Or create one any time:

```bash
npm run prisma-auth-seed -- <username> <password> [admin]
```

If the auth setup step fails, rerun it with `npm run prisma-auth-setup`. Note
that `prisma/dev.db` is tracked in git, so the push modifies it in your working
tree; don't commit it with your own users in it.

Orion and Artemis protobuf and Prisma definitions are generated by Bazel from `lib/spec`;
there are no editable Orion copies in this package. `npm run protobuf-orion`
builds the shared protobuf. The Kafka consumer reads `ORION_PROTO_PATH` when
explicitly set, otherwise the generated file under the checkout's
`bazel-bin/lib/codegen/telemetry/`. Missing outputs must be built, not replaced
by a checked-in fallback.

`npm run prisma-orion-generate` and `npm run prisma-artemis-generate` build the
generated schemas and stage them under ignored `.prisma/` for Prisma module
resolution. Clients are generated into `.prisma/<car>-client`. Artemis generation
also builds its storage contract and protobuf.
It is part of `postinstall`; it does not connect to or migrate the database.

Build the protobuf artifacts:

```bash
bazel build //apps/telemetry:new_car_schema_proto
npm run protobuf-orion
```

Run dev server:

```bash
npm run dev
```

## Hosting

The viewer is self-hosted: `npm run build` + `npm start` on the telemetry
box, kept up by PM2 (see [the stack README](../../../stack/README.md)) and
reached through a Cloudflare tunnel. Nothing in this directory targets
Vercel; the `lapdog` Vercel check that used to post on PRs belonged to the
removed standalone drive day app and is managed in Vercel's dashboard, not
here.

## Trackside live

`/trackside-live` is the pit-wall page: live samples from Kafka, lap timing,
energy plan, driver dash. Lap controls, in the Live Laps panel:

- **Start Lap / Log Lap** starts the timer, then closes a lap and re-arms the
  next one (a loop). **Stop Lap** closes the lap without re-arming, for
  autocross, accel and skidpad runs where the drive back is not a lap; Start
  Lap arms the next run. Both are leader-only.
- **Add time** enters a lap by its duration (`m:ss.ss` or seconds) when the
  official timing or a stopwatch has it and the page does not. It is a
  `manual` lap with no samples, sectors or energy, so it counts toward laps
  and the average and nothing else.
- A new session is named `<venue> · <event type> N · YYYY-MM-DD`, N counting
  this browser's sessions of that type today; type over it if you want.

The page keeps the last 6,000 samples in memory and in the JSON export, so
at 20 Hz the export holds the last 5 minutes of samples and at 50 Hz the last
2 minutes (laps keep their times either way). The full stream is in Postgres.

## Drive day viewer

`/trackside-retro` replays a trackside-live session export after the fact:
map with sectors, lap timeline, corners and braking zones, cell temperatures,
energy plan. It runs entirely in the browser and keeps its data in IndexedDB.
How it sorts lap presses into courses, where the export comes from and how to
test it are in [src/lib/driveday/README.md](src/lib/driveday/README.md);
`npm run test:driveday` runs its tests.

## LAPDOG refresh

Trackside Retro includes the current LAPDOG video/track/analysis workspace,
wheel-zoom timeline, route-matched cross-file comparisons, GPS-quality checks
and driving debrief tools. Drive days load only from the database; Trackside
event notes come with them. See [the retro guide](src/lib/driveday/README.md).

Video playback copies are made locally using `ffmpeg-static`.
`npm run dev` and `npm start` launch the loopback helper; remote users run
`npm run video-helper -- --origin https://your-viewer-host.example` on their
own computer. Originals are not uploaded to the viewer server. See
[helper setup](tools/README.md). No database setup is needed for the helper.

## Database reads

Orion retains packet-based reads and packet ranges. Artemis uses time windows
and the generated frequency-pool read interfaces below. Retired cars are not
accepted as live sources.

The active Artemis database client is generated by Bazel during
`prisma-artemis-generate` (now part of `postinstall`). It builds the storage
contract as well as the Prisma models; generated artifacts remain outside git.
Set `ARTEMIS_DATABASE_URL` to override the existing `ARTEMIS_DB_*` connection
settings. `ARTEMIS_STORAGE_CONTRACT_PATH` explicitly overrides the generated
contract path when deploying artifacts outside the checkout.

Artemis replay uses drive-day start/end times and session/time sample keys.
Replay returns fields from the selected raw nanosecond sample and recording;
it preserves peaks and leaves missing subsystem fields absent rather than
averaging the following 100 ms. See the [replay reader](src/lib/prisma/README.md).
Trackside Retro database exports and MoTeC series use the generated Timescale
bucket functions, aligning each pool before combining subsystems. The bucket
widens to the slowest participating periodic pool; cell arrays require at least
one second. Logical channel names stay the same. Live widgets continue to read
Kafka and do not wait for database bucketing.

`GET /api/motec/series` accepts `aggregate=avg|min|max|last` for Artemis floating
channels (default `avg`). Arrays and states retain the last sample. The handshake
returns `latest_sample_ms` and preserves `last_packet` for Orion; Artemis replay returns `session_start_ms`, not a
packet identifier. No Artemis packet-table compatibility layer is installed.

Artemis telemetry reads use the shared gateway; Prisma remains for application
metadata and legacy readers. Clients are generated only: never run `db push`
against telemetry data.


The isolated [gateway integration runner](../../../stack/tests/README.md)
exercises real Kafka, Timescale, mixed-rate queries and Grafana. `npm run
test:driveday` runs the viewer's browser-analysis tests independently of that
Docker stack.

For existing shared metadata databases, `npm run prisma-cars-register` registers
Orion ID 5 and Artemis ID 6 through Prisma without deleting old drive days or
lookups. It refuses an ID already assigned to a different name. Fresh stack
initialization includes both. See [existing-volume setup](../../../stack/README.md).
