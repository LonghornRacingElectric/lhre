# Telemetry analysis

Python analysis and database access used by ingest and the stack processors.
`//apps/telemetry/analysis:analysis_lib` is the shared Bazel library.

Application reads use `GatewayClient` from `analysis.query_client`, backed by
`QUERY_GATEWAY_URL` and `QUERY_API_TOKEN`. It provides discovery, sessions,
paged queries and SSE streams through the existing API. Nanosecond identity and
large integer values stay decimal strings. `query()` discards partial pages on
an error, including `409 query_changed`; callers restart the whole query.
Stream events expose coverage gaps and replacement windows without silently
retrying or appending duplicate rows. The client adds no result cache.

`bazel test //apps/telemetry/analysis:query_client_test` checks pagination,
conflicts and stream handling. See the [application guide](database/README.md)
for the generated Artemis publisher and full-stack validation.
The publisher retains the `DataTester` generator/description helpers, profiles,
row-count/delay controls, and CSV mapping, adapted to native Artemis batches and
logger CSVs. Its shared library is `//apps/telemetry/analysis:paho_testing`.

Orion ORM classes are generated from the textproto by
`//lib/codegen/telemetry:orion_models`, not synchronized into this tree.
Existing imports from `sql_utils.models` still work through its re-exports.
Artemis models are generated by `:artemis_models` for time-based frequency pools.
Shared event/track metadata stays hand-maintained. Angelique and Nightwatch
are retired; unqualified analysis aliases now select Orion.

See [SQL utilities](sql_utils/README.md) and
[the viewer](database/viewer_tool/README.md) for consumers.

## Board health demo

`database/paho_testing.py --replay` publishes the recorded UTA autocross run
(`database/data/`) to MQTT `artemis/data` as the car's `TelemetryBatch`
messages, looped at its recorded pace and restamped to now. Add
`--dropout-board dui --dropout-after 20 --dropout-for 10` to make one board stop
reporting: its `last_seen_s` climbs past board_health's 0.5 s threshold, goes
STALE, then recovers. Replay needs the stack running but not the database.

```
bazel run //apps/telemetry/analysis:publish_demo -- --replay --dropout-board dui
```

The **Board Health - Artemis (Real-time)** dashboard
(`database/dashboards/artemis/board_health.json`) graphs each board's
`last_seen_s` against the threshold. `bazel test
//apps/telemetry/analysis/tests:artemis_replay_test` replays the recording
through the real decoder and board_health's tracker.

## CAN-to-client demo verification

The [two-laptop runbook](../../BEVO/nonhermetic/DEMO.md) starts with SocketCAN
and updater-installed binaries. Run `//apps/telemetry/analysis:verify_can_demo`
with `--evidence /tmp/can-demo.json` to observe seven channels through the
gateway, check freshness, save resolved live identities/values and compare a
query over the same time range. It reports provisional results without calling
them persisted. It sends no telemetry. Set `QUERY_API_TOKEN` and
`QUERY_GATEWAY_URL` on the server.

After stopping the sender, closing live clients and restarting the gateway, use
`--check /tmp/can-demo.json --require-postgres` to verify those observations
through storage. Coverage errors and value mismatches fail; pagination revision
changes restart the historical read within a bounded wait. This is a manual
deployment check, not automatic GHCR publication or hardware CI.
`bazel test //apps/telemetry/analysis:verify_can_demo_test` checks live-to-history
matching and rejects altered values or missing samples.
