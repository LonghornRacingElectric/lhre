# ADR-008: One CAN spec in textproto; all derived artifacts generated

- **Status:** Accepted
- **Date:** 2026-08

## Context

The previous car's CAN pipeline (`lhre-2026`) generated firmware code
from CSVs, but the telemetry side kept several hand-maintained,
name-keyed copies of the field list: a Go bridge map and SQL columns.
When a copy drifted, values did not error. They read as zero on
dashboards. The CSV cell syntax also packed encoding, proto typing, and
field ids into a string DSL only the scripts could parse, and nothing
validated cross-file consistency on a clean checkout.

## Decision

One spec, in textproto files under [lib/spec/](../../lib/spec/README.md),
describes every message's wire encoding, logical meaning, and telemetry
mapping as three separate layers. Every derived artifact is generated by
hermetic Bazel rules: the firmware pack/unpack library
([lib/codegen/cpp](../../lib/codegen/cpp/README.md)), and later the
snapshot proto, gateway tables, ingest helpers, DBC, and docs.

Load-bearing choices:

- **Textproto over YAML.** The meta-schema
  ([can_spec.proto](https://github.com/LonghornRacingElectric/lhre/blob/main/lib/spec/proto/can_spec.proto))
  doubles as the IR, so the spec and its outputs share one type system
  and the parser gives structural validation for free. The loader is
  isolated in one small module so swapping syntax later is cheap.
  Comments are schema fields, since the canonical serializer cannot
  round-trip textproto comments.
- **Stateless validation.** `bazel test //lib/spec:validate` is a pure
  function of the spec files. Telemetry ids are append-only per group,
  enforced by a partition invariant over each group's ledger. Id
  recycling, forgotten tombstones, and cross-branch merge collisions all
  fail on a clean checkout with no reference to git history.
- **Wire types are derived** from sign, width, scale, and offset rather
  than declared, so a signal's encoding and its server-side type cannot
  disagree. `lib/spec/wire.lock` commits the resulting field numbers and
  types, since changing a scale changes a live field's type without
  changing its id.
- **Raw integers on-board, physical values off-board.** Generated
  structs carry raw wire values with integer-only pack/unpack. Float
  conversion is separate, and raw to physical happens once at the
  gateway.
- **One file per source board**, with `from_board` enforced to match, so
  codegen emits one namespace and library per board and firmware links
  only the message sets it uses.
- **Rate tiers are orthogonal to groups.** Publish rate never affects
  proto structure, so a tier change cannot renumber fields.

Phase 1 implements the spec, validator, formatter, editor, and firmware
C++ library. Telemetry generators follow the same design; their schema
and ledgers are already live and validated.

## Alternatives considered

- **Keep CSV and scripts.** The failure mode being fixed. The cell DSL
  has no schema, and hand-synced consumers stay possible.
- **YAML and pydantic.** Friendlier syntax, but a second type system to
  keep aligned with the proto outputs, and structural validation has to
  be written by hand. Cheap to revisit through the isolated loader.
- **DBC as the source.** Standard tooling reads it, but it cannot carry
  telemetry mapping, ledgers, or ownership metadata. It stays an output
  for third-party CAN tools.
