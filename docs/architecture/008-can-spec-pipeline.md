# ADR-008: One CAN spec in textproto; all derived artifacts generated

- **Status:** Accepted
- **Date:** 2026-08

## Context

The previous car's CAN pipeline (`lhre-2026`) generated firmware code
from CSVs, but the telemetry side kept several hand-maintained,
name-keyed copies of the field list (a Go bridge map, SQL columns).
When a copy drifted, values didn't error — they silently read as zero
on dashboards. The CSV cell syntax also packed encoding, proto typing,
and field ids into an ad-hoc string DSL that only the scripts could
parse, and nothing validated cross-file consistency on a clean
checkout.

## Decision

One spec, in textproto files under [lib/spec/](../../lib/spec/README.md),
describes every message's wire encoding, logical meaning, and telemetry
mapping as three separate layers. Every derived artifact — the firmware
pack/unpack library ([lib/codegen/cpp](../../lib/codegen/cpp/README.md)), and next the
snapshot proto, gateway tables, ingest helpers, DBC, and docs — is
generated by hermetic Bazel rules. Nothing downstream is hand-written.

Load-bearing choices:

- **Textproto over YAML.** The meta-schema
  ([lib/spec/proto/can_spec.proto](https://github.com/LonghornRacingElectric/lhre/blob/main/lib/spec/proto/can_spec.proto))
  doubles as the IR — the pipeline already emits proto, so the spec and
  its outputs share one type system, and the parser gives structural
  validation for free. The loader is isolated in one small module so
  swapping syntax later is cheap. Comments are schema fields
  (`description`), not textproto comments, because the canonical
  serializer can't round-trip the latter.
- **Stateless validation.** `bazel test //lib/spec:validate` is a pure
  function of the spec files. Proto field ids are append-only per
  telemetry group, enforced by a partition invariant over each group's
  ledger (live ∪ reserved = {1…next_free−1}, disjoint) — id recycling,
  forgotten tombstones, and cross-branch merge collisions all fail on a
  clean checkout with no reference to git history or prior outputs.
- **Raw integers on-board, physical values off-board.** Generated
  message structs carry raw wire values with integer-only pack/unpack
  (float conversion accessors are separate), and the raw→physical
  conversion happens exactly once at the gateway. The CAN bit layout never leaks
  past the firmware/gateway boundary.
- **Rate tiers ⊥ semantic groups.** Publish rate is a per-signal
  attribute (with message default and frequency-derived fallback) and
  never affects proto structure — a tier change can't renumber fields.
- **One canonical serialization**, shared by the formatter, format
  check, and every future spec-writing tool, so all edits converge to
  identical bytes.

Phase 1 (this ADR's landing) implements the spec, validator, formatter,
and firmware C++ library. Telemetry-side generators follow the same
design when built; the schema and ledgers for them are already live and
validated.

## Alternatives considered

- **Keep CSV + scripts.** The failure mode being fixed. The cell DSL
  has no schema, and hand-synced consumers stay possible.
- **YAML + pydantic.** Friendlier syntax, but a second type system to
  keep aligned with the proto outputs, and structural validation must
  be written by hand. Revisitable cheaply via the isolated loader.
- **DBC as the source.** Standard tooling reads it, but it can't carry
  telemetry mapping, ledgers, or ownership metadata; it stays what it's
  good at — an *output* for commercial CAN tools.
